# 产品采集模块优化方案

> **状态：B 档已实施（分支 `feat/scrape-optimize`，2026-09-11）；A 档与 C 档待决策。**
> 本文档记录 2026-09-11 的诊断结论与分级方案，供后续参考。
> 实施前请先核对代码现状（下方标注的行号会随改动漂移）。

## 1. 诊断数据（2026-09-11 实测）

| 指标 | 实测值 | 来源 |
|---|---|---|
| 单个商品页响应耗时 | 7~10 秒 | 直接抓取计时，页面 1.8~2.5 MB |
| 单次采集有效响应率 | 约 80%（40/50） | 任务 `st4bdda80fa949` 第一块 |
| 500 个 ASIN 总耗时 | **92 分钟** | 10 块 × 9.2 分钟 |
| 实际请求速率 | **8.7 请求/分钟** | 800 次请求 ÷ 92 分钟 |
| 令牌桶允许速率 | 40 请求/分钟 | `SCRAPER_REFILL_MS=1500` |
| 解析耗时 | 0.25~1.25 秒/页 | 非瓶颈，`html.parser`（lxml 未安装） |

**结论：额度只用了不到四分之一，绝大部分时间是空转与等待，不是被限流卡住。**

## 2. 根因

1. **前端把批次切得过碎**：`ProductScrape.tsx:35` 的 `BATCH_SIZE = 3`，500 个 ASIN 变成
   **167 次串行 POST**，每次 POST 之间后端完全空闲。
2. **后端「批大小」与「并发数」共用一个变量**：`product_fetcher.py:1305`
   `batch_size = max(1, int(os.environ.get("SCRAPER_CONCURRENCY", "3")))`，
   所以内部分批也是 3 个一批，每批之间还有 `human_delay`。
3. **失败重试轮的固定等待**：`product_fetcher.py:1350`
   `time.sleep(min(5 + len(failed_indices) * 1.0, 15))`，每次 `scrape_products` 调用都执行一次。
   前端每批只带 3 个时，这一句几乎每批都触发，等于每 3 个 ASIN 白等 6 秒起。
4. **stagger 按位置线性叠加**：`product_fetcher.py:1320`
   `pos * stagger_base + random.random() * jitter`，40 个一批时末位要白等约 15.6 秒。

## 3. 分级方案

### A 档：缺陷修复（不改变任何操作方式）

**A1. 结果表存在重复行**

- 现状：`scrape_products` 只有 `idx_scrape_prod_task` 索引，**没有唯一约束**；
  `db.py` 的 `save_scrape_products` 用普通 `INSERT`。
- 后果：「重试失败项」对同一 ASIN 会再插一行，同一任务同一 ASIN 最多 3 条。
  实测现有 **106 组重复**。`get_scrape_products` 也不去重 → 结果列表出现重复行，
  成功/失败统计虚高。
- 修法：导出备份 → 清理重复（每对 `(task_id, asin)` 保留 id 最大的一条）→
  建 `UNIQUE INDEX (task_id, asin)` → 写入改 `ON CONFLICT DO UPDATE`。
- 风险：**无**。清理前先备份到 `data/`。

**A2. 任务状态语义失真**

- 现状：`db.py` 的 `accumulate_scrape_task` 每次写入都执行
  `UPDATE ... status='completed'`。
- 后果：任务还在跑，任务列表里已经显示为已完成。
- 修法：拆成「累加计数」与「显式设置状态」两个方法。
- 风险：**无**。

### B 档：消除空转（不动任何限流参数）⭐ 收益最大

以下四条只改「批次怎么切」。**令牌桶容量、补充间隔、最小请求间隔、并发数一概不动**，
所以「每分钟最多发几个请求」与现在完全一致，封禁风险不变。

| # | 改动 | 说明 |
|---|---|---|
| B1 | 前端 `BATCH_SIZE` 3 → 50 | 167 次 POST 降到 10 次；同时减少前端重复渲染与写库次数 |
| B2 | 新增 `SCRAPER_BATCH_SIZE`（默认 40），与 `SCRAPER_CONCURRENCY` 解耦 | 批大、并发小 → worker 始终有活干，不再反复重建线程池 |
| B3 | `stagger` 只对「同时启动的那一批」生效 | 排队中的任务会被空闲 worker 自然错开，不需要再叠加位置延迟 |
| B4 | 失败重试轮改为固定短等待 | 失败项在 `fetch_product_page` 内部已退避过 2/5/10 秒，这里不必再等 5~15 秒 |

**预估收益：92 分钟 → 约 35 分钟。**

**实施结果（2026-09-11，分支 `feat/scrape-optimize`）**：四条已全部落地。
用假抓取任务（每个耗时 1.0 秒）在 40 个 ASIN 上实测，各跑 2 轮取均值：

| 配置 | 耗时 | 峰值并发 |
|---|---|---|
| 旧：批 3 / 并发 3 | 33.44s | 3 |
| 新：批 40 / 并发 3 | **15.48s** | 3 |
| 新：批 40 / 并发 6 | **8.92s** | 6 |

即只做 B 档就有 **2.2 倍**提升，且请求速率上限完全未变。

> ⚠️ 只做 B 档时，**新瓶颈会变成并发数**：3 并发 ÷ 8 秒/请求 ≈ 22.5 请求/分钟，
> 仍然填不满 40 的闸门。要再往下压需要 C1。

### C 档：可选项（会改变行为，需明确同意）

**C1. 并发 3 → 6**

- 效果：把 35 分钟压到 **20~25 分钟**。
- 风险：请求更接近 40 req/min 的上限，但不会突破（令牌桶仍是硬闸门）。

**C2. 错误分流**

- 现状：`RETRY_DELAYS = [2.0, 5.0, 10.0]` 对所有失败一视同仁。
- 改法：网络抖动（`neterr:URLError`）快速重试（0.5~1 秒）；仅 202 / 503 / CAPTCHA 用长退避。
- 收益：压掉一部分无效等待。

**C3. 避免重复采集**

- 同一个 ASIN 若近期（如 7 天内）已采集过，提示或跳过。
- 收益：省配额与时间。
- 代价：可能拿不到最新数据，因此需用户显式选择。

**C4. 任务可续跑（不做异步化改造）**

- 只记录任务的完整 ASIN 列表与已成功项（`scrape_tasks` 加一列 `asins`），
  前端加一个「继续」按钮，从断点接着跑。
- 解决「刷新页面就白跑一轮」，但不引入后台执行线程。
- 代价：任务卡上会多一个小按钮。

## 4. 不建议做的

- **异步化 / 服务端后台执行**：2026-09-11 曾实现并验证通过，随后应要求整体回滚。
  在用户没有明确要求前不再推进。
- **任何会自动中止任务的「智能」判定**（例如判定 IP 被限流后主动停止）：
  同一日已验证，用户明确表示不要这类会替他拿主意的逻辑。
- **提高令牌桶速率上限**：这是唯一真正改变封禁风险的参数，保持现状。

## 5. 实施注意事项

- A1 涉及数据清理，务必先导出备份到 `data/`，并保证迁移幂等。
- 若只实施 A + B，`compiled/bundle.js` 属于构建产物（已被 `.gitignore` 忽略），
  改完前端源码必须重新 `npm run build`，否则界面与后端对不上。
- B 档改完后建议先跑 50~100 个 ASIN 的小任务复核耗时，再上大批量。
